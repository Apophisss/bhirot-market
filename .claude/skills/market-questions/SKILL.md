# צינור השאלות של בחירות מרקט

`AGENT.md` אומר **מה** רוטינת העדכון עושה בכל ריצה. הסקיל הזה אומר **איך מחליטים** — איך מוצאים
שאלה, איך מוודאים שהיא בכלל ניתנת להכרעה, איזה אחוז לתת לה, וכמה גמיש צריך להיות השוק שלה.
כשיש סתירה — `AGENT.md` והסכמה ב-`src/lib/content.ts` גוברים.

## הצינור

```
1. חיפוש    → 10–20 מועמדים גולמיים מהחדשות
2. ווידוא   → 9 שערים; מי שנופל בשער אחד — נזרק או מנוסח מחדש
3. תמחור    → initialProbability מתוך בסיס־שכיחות + התאמות
4. גמישות   → liquidity לפי npm run markets:liquidity
5. הרכבה    → batch.json → markets:merge → markets:validate → markets:audit
6. הכרעות   → שווקים שמועד היעד שלהם עבר
7. commit + push (+ דחיפה ל-API אם יש SITE_URL ו-ADMIN_TOKEN)
```

היעד בכל ריצה: **2–6 שאלות חדשות**, לפחות שליש מהן נסגרות תוך 24–72 שעות. פחות שאלות טובות
עדיף על יותר שאלות בינוניות. ריצה בלי חדשות אמיתיות = ריצה בלי commit.

## 1. חיפוש

התחילו מ-`npm run markets:audit` — הוא אומר מה כבר יש, איפה חורים, ומה מחכה להכרעה. אחר כך
חפשו (עברית ואנגלית, 24–72 השעות האחרונות) בשני מסלולים במקביל:

- **חדשות** — מה קרה: סקר חדש, הודעת מיזוג, הגשת עתירה, ריאיון, החלטת ועדה, פיצוץ קואליציוני.
- **יומן** — מה *עומד* לקרות: מועדי חוק הבחירות, ישיבות ממשלה וכנסת, דיוני בג"ץ, לילות סקרים
  קבועים. שאלה על אירוע שכבר קבוע ביומן היא השאלה הכי קלה לכתוב ולהכריע.

לכל מועמד רשמו בשורה אחת: מה האירוע, מי המקור המכריע, מתי נדע. אם אי אפשר למלא את שלושתם —
אין שאלה. פירוט — לוח המועדים הקבוע, ארכיטיפים של שאלות ושאילתות חיפוש: `references/research.md`.

## 2. ווידוא

כל מועמד עובר את תשעת השערים. כישלון בשער = זריקה או ניסוח מחדש, אף פעם לא "בערך בסדר":

| שער | השאלה שאתם שואלים | נפילה טיפוסית |
|---|---|---|
| 1. הכרעה | האם ב-1.1.2027 אפשר לומר כן/לא בלי ויכוח? | "האם נתניהו ייחלש?" |
| 2. מקור | מי בדיוק מכריע — כלי תקשורת ספציפי, פרוטוקול, פרסום רשמי? | "לפי הדיווחים" |
| 3. חזרה יבשה | האם ריצה עתידית, עם חיפוש ו-WebFetch בלבד, תמצא את הראיה אחרי המועד? | ראיה שקיימת רק בשידור חי |
| 4. מקרה השלילה | מה קורה אם האירוע פשוט לא קורה בחלון? | קריטריון שמדבר רק על "כן" |
| 5. טרם קרה | האם האירוע כבר קרה בזמן הכתיבה? | שאלה שנולדה מוכרעת |
| 6. אין כפילות | האם קיימת שאלה פתוחה על אותו אירוע? | ניסוח שונה, אותו אירוע |
| 7. מקורות אמיתיים | האם כל URL נפתח ותומך בטענה? | קישור שהומצא מהזיכרון |
| 8. מותר | לא מוות/בריאות, לא עידוד אלימות, לא הצגת מחלוקת כעובדה | — |
| 9. כותרת קצרה | האם הכותרת נכנסת בשלוש שורות בכרטיס? | 140 תווים עם שלושה סעיפי משנה |

**שער 3 — מי יכריע את זה בפועל.** את השאלה הזאת יכריע *סוכן*, לא עיתונאי: ריצה עתידית של הרוטינה,
שיש לה חיפוש ו-WebFetch ותו לא. היא לא ראתה את השידור, אין לה מנוי, והיא לא הייתה שם. לכן הראיה
חייבת להשאיר **עקבה פומבית וכתובה** שאפשר יהיה למצוא ימים אחרי המועד. לפני ההגשה עשו חזרה יבשה:
הריצו *עכשיו* את החיפוש שהריצה העתידית תריץ, על האירוע המקביל האחרון — אם היום הוא לא מחזיר עמוד
שמכריע, גם בעוד שבועיים הוא לא יחזיר.

**שער 7 הוא הקשה: אין להמציא כתובות.** כל קישור נבדק ב-WebFetch לפני שהוא נכנס לקובץ.

**שער 9 — הכותרת היא כרטיס, לא פסקה.** יעד: **עד 80 תווים** (בערך 12 מילים); מעל 120 ה-audit
מתריע; הסכמה חוסמת ב-180. הכותרת נושאת רק את מה שמבדיל — מי, מה, סף, מועד — וכל השאר
(שעה מדויקת, חריגים, רשימת כלים) יורד ל-`resolutionCriteria`, והרקע ל-`subtitle`.

פירוט מלא, כולל ניסוחים לדוגמה ובדיקת כפילות מול `merge-markets.ts`: `references/validation.md`.

## 3. תמחור — `initialProbability`

מתחילים מבסיס־שכיחות של סוג השאלה, ואז מתקנים. **לא מתחילים מ-50%.**

| סוג שאלה | נקודת פתיחה |
|---|---|
| אירוע דרמטי לא מתוזמן, חלון 24–72 שעות | 5–15% |
| אירוע שכבר קבוע ביומן, יקרה כמתוכנן | 80–92% (בישראל דוחים הרבה) |
| סקר קבוע יתפרסם בכלל בחלון של שבוע | 85–95% |
| סקר חוצה סף מנדטים | לפי הפער מהממוצע — טבלה ב-`references/pricing.md` |
| הוגשה כוונה משפטית → כתב תביעה בפועל | 30–50% בדדליין רחוק, פחות בקרוב |
| מיזוג/רשימה משותפת לפני דדליין חוקי | קופץ סמוך לדדליין, נמוך לפניו |
| החלטת בג"ץ/יועמ"ש עד תאריך | מתחת ל-30% אם אין דיון קבוע |
| הופעה תקשורתית של פוליטיקאי בקמפיין | 70–90% לשבוע, 40–60% לכלי ספציפי ב-72 שעות |

תיקונים: כוונה מוצהרת ומפורשת (+), תאריך קבוע ביומן (+), כל שחקן נוסף שחייב להסכים (×0.7),
היסטוריה של דחיות אצל אותו שחקן (−), חלון שכולל שבת/חג (−).

**האחוז הוא גם מבחן איכות לשאלה.** אם ההערכה הכנה יצאה מתחת ל-15% או מעל 85% — השאלה משעממת:
הזיזו את הסף (25 מנדטים במקום 30), קצרו או האריכו את המועד, עד שהיא נוחתת ב-**0.15–0.85**.
מחוץ ל-0.05–0.95 אסור להגיש בכלל. אל תעגלו ל-0.5 כי לא הספקתם לחקור — 50% זו קביעה שצריך
להצדיק בראיות משני הצדדים.

טבלת סקרים כמותית, הטיות בית של כל מכון, דוגמאות מלאות ומלכודות: `references/pricing.md`.

## 4. גמישות השוק — `liquidity`

`liquidity` הוא ה-`b` של ה-LMSR: קנה המידה בשקלים שעליו המחיר זז. הוא נכתב למסד **רק כשהשוק
נוצר** (`upsertMarkets` ב-`src/lib/sync.ts`) — שינוי שלו ב-JSON אחרי שהשוק עלה לא משנה כלום
באתר, רק יוצר פער בין הקובץ למסד. לכן מחליטים אותו פעם אחת, לפני ה-commit הראשון.

```bash
npm run markets:liquidity -- --p 0.3                 # השוואת כל הערכים בסולם
npm run markets:liquidity -- --p 0.3 --traffic hot   # לשאלה שתוביל את הדף הראשי
npm run markets:liquidity -- --p 0.3 --b 2000        # פירוט מלא לערך אחד
npm run markets:liquidity -- --audit                 # כל השווקים הפתוחים
```

הכלל: **2000 (ברירת המחדל של האתר) אלא אם יש סיבה.** הכלי בודק שני מספרים — כמה הימור רגיל
של ₪100 מזיז את המחיר (יעד: 1–8 נקודות אחוז) וכמה ₪1,000 של שחקן אחד מזיזים (תקרה: 40).

| מצב | liquidity |
|---|---|
| שאלה רגילה | 2000 |
| `featured`, שאלה שתוביל את הדף הראשי | 4000 — הרבה מסחר לא יקפיץ את המחיר |
| שאלה נישתית ל-48 שעות שרק מעטים יסחרו בה | 1000 — כדי שהמחיר בכלל יזוז |
| הכלי אומר `thin`/`thick` | קחו את מה שהוא ממליץ, לא את ברירת המחדל |

הסבר מלא של המנגנון ומתי לחרוג: `references/liquidity.md`.

## 5. הרכבה, מיזוג ובדיקה

כתבו batch לפי `templates/batch.example.json` (כולל `newPeople` אם צריך אנשים חדשים), ואז:

```bash
npx tsx scripts/merge-markets.ts batch.json --note "תקציר בעברית של מה נוסף"
npm run people:fetch          # רק אם נוספו אנשים
npm run markets:validate      # סכמה — חייב לעבור
npm run markets:audit         # בריאות הלוח — תקנו כל ✗, שקלו כל ⚠
npm test                      # אינווריאנטות של מנוע השוק
```

`merge-markets.ts` דוחה לבד slug כפול, כותרת שדומה ב-0.8 לשאלה קיימת, ו-`closesAt` קרוב מדי.
הבדיקה הזו רואה רק כותרות — כפילות אמיתית נמדדת בקריטריון ההכרעה, ראו `references/validation.md`.
דחייה היא תשובה, לא תקלה — אל תעקפו אותה בשינוי מילה בכותרת.

## 6. הכרעות

בכל ריצה, לפני שמוסיפים: `npm run markets:audit` מציג תחת "resolution debt" כל שוק פתוח שמועד
היעד שלו עבר. הכריעו לפי `AGENT.md` — עם ראיה פומבית ומקור, `NO` אם המועד עבר והאירוע לא קרה,
`cancelled` אם השאלה התבררה כלא ניתנת להכרעה. אל תשנו `initialProbability`, `liquidity` או
`slug` של שוק קיים.

זו החזרה היבשה של שער 3 באמת: מריצים את החיפוש שהשאלה הבטיחה, פותחים ב-WebFetch את העמוד
שהוא מחזיר, ומעתיקים את ה-URL ל-`resolutionNote`. שוק שלא הצלחתם להכריע ככה — רשמו בריצה מה
חסר; אם גם בריצה הבאה אין ראיה פומבית, זה `cancelled`, וזו שאלה שהייתה צריכה להיפסל בשער 3.

מקטע ה-**calibration** ב-audit מנקד את כל ההכרעות שהצטברו (Brier, הטיה שיטתית, אמינות לפי
רצועות): הוא התשובה לשאלה "האם האחוזים שלנו טובים בכלל", והוא הקלט לתמחור של הריצה הבאה.
אם הוא אומר שאתם אופטימיים בשיטתיות — הורידו את נקודות הפתיחה בטבלה שלמעלה.
